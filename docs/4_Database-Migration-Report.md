## 3. Differences from `schema-tables.sql` (all intentional / cosmetic)

1. **PK identity → serial.** The SQL doc declares `BIGINT GENERATED BY DEFAULT
   AS IDENTITY`; Laravel `$table->id()` emits `bigint` + sequence (`nextval`).
   Both auto-increment and both allow explicit id inserts. Approved; keep
   Laravel default. (Identity columns report `is_identity=YES`; serial does
   not — the catalog difference is expected.)
2. **Timestamp precision.** Laravel emits `timestamp(0)` (seconds) +
   `CURRENT_TIMESTAMP`; the SQL doc declares microsecond `TIMESTAMPTZ`
   `DEFAULT now()`. Application code never writes microseconds (Eloquent
   default date serialization), so behavior is identical. Accepted.
3. **`users.email` unique name.** The scaffold migration names it
   `users_email_unique` instead of `uq_users_email`. Same semantics.
4. **Index-backed uniques.** The one-active partial rules
   (`uq_section_lecturers_primary`, `uq_student_programs_active`,
   `uq_internships_active`) are unique **indexes** in both the SQL doc and the
   migrations (implemented via `DB::statement`, predicates verified).
   `uq_gpa_records` (`UNIQUE NULLS NOT DISTINCT`) is a table CONSTRAINT in the
   SQL doc but a unique INDEX in the migration — PostgreSQL supports either
   form; enforcement is identical.
5. **Default-expression notation.** Numeric/boolean defaults differ only in
   catalog serialization (`'100'::numeric` vs `100`, `'0'::smallint` vs `0`);
   the stored default values are identical.
6. **Reserved word `settings.group`.** Works in the migrations (Laravel quotes
   identifiers). The raw SQL doc previously failed on `CREATE INDEX
   idx_settings_group ON settings (group)`; the doc now quotes `"group"` and
   was re-verified to execute as-is with `ON_ERROR_STOP=1`.
7. **Framework tables.** `cache`, `cache_locks`, `jobs`, `job_batches`,
   `failed_jobs`, `sessions`, `password_reset_tokens`,
   `personal_access_tokens` exist in the app DB (Laravel scaffold) but are out
   of scope for the SQL doc. `notifications` is a domain table and is included
   in the 49.
8. **`users` scaffold alignment.** `0001_01_01_000000` creates
   `created_at/updated_at/email_verified_at` as `timestamp` (nullable);
   migration `130005` now converts them to `timestamptz` with
   `created_at/updated_at` `NOT NULL DEFAULT now()` per the spec.

## 5. How to reproduce

```bash
# from repo root (compose file lives at docker/docker-compose.yml)
docker compose --project-directory . -f docker/docker-compose.yml up -d postgres backend

# reference DB: load the SQL doc verbatim (pipe into psql with -i, or cp+`-f`)
docker compose --project-directory . -f docker/docker-compose.yml exec -i postgres \
  psql -U educore -d educore -v ON_ERROR_STOP=1 -c "CREATE DATABASE educore_verify"
# ...and repeat to create educore_ref, then:
docker cp docs/database/schema-tables.sql educore-postgres:/tmp/schema-tables.sql
docker compose --project-directory . -f docker/docker-compose.yml exec -T postgres \
  psql -U educore -d educore_ref -v ON_ERROR_STOP=1 -f /tmp/schema-tables.sql

# migrations: run into the scratch DB (override DB_DATABASE)
docker compose --project-directory . -f docker/docker-compose.yml exec -e DB_DATABASE=educore_verify \
  -w /var/www/html backend php artisan migrate:fresh --force
docker compose --project-directory . -f docker/docker-compose.yml exec -e DB_DATABASE=educore_verify \
  -w /var/www/html backend php artisan migrate:status
```

Then diff pg_constraint / pg_indexes / information_schema.columns between
`educore_ref` and `educore_verify` (a `schema_report.sql` catalog-dump query
set is kept in the opencode session temp area / can be recreated on request).

(Production `educore` DB is currently empty of business data; `migrate:fresh`
is safe in dev.)
