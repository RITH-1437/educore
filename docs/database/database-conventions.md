# EduCore Database Conventions

Naming and structural rules for the EduCore PostgreSQL schema. These mirror
`skills/database/SKILL.md` and `skills/academic-domain/SKILL.md` — where a
conflict exists, the skill wins.

## 1. General

- Language: PostgreSQL 16. Charset: UTF-8 (default).
- All schema changes are made through Laravel migrations (`php artisan
  make:migration`) — never by hand in production.
- Every table gets `created_at` / `updated_at` (`timestamps`).
- Timezone: `timestamptz` (`timestamp with time zone`) for instants;
  `date` for academic/business dates (no time component).

## 2. Tables

| Rule | Convention | Example |
|---|---|---|
| Case | snake_case | `course_offerings` |
| Number | plural | `faculties`, `enrollments` |
| Pivot | plural, alphabetical (or skill-named) | `course_programs`, `section_lecturers` |
| Prefix | none | ✅ `semesters` ❌ `acad_semesters` |

## 3. Columns

| Rule | Convention | Example |
|---|---|---|
| Case | snake_case | `first_name` |
| Foreign key | `<entity>_id` | `program_id`, `section_id` |
| Boolean | `is_*` / `has_*` | `is_active`, `is_published` |
| Timestamp | `*_at` | `enrolled_at`, `published_at` |
| Date | `*_date` / `*_on` | `due_date`, `paid_on` |
| Money | `*_amount` / `amount` | `total_amount` (see §7) |
| Soft delete | `deleted_at` | default |

## 4. Primary keys

- Strategy: **`bigint` auto-increment `id`** — `id BIGINT GENERATED BY DEFAULT
  AS IDENTITY PRIMARY KEY`.
- One strategy for every table; never mix UUID/ULID into `id`.
- Business/public identifiers are **separate columns** with their own UNIQUE
  constraints: `students.student_number`, `lecturers.staff_number`,
  `invoices.invoice_number`, `documents.verification_token`,
  `universities.code`, `courses.code`.
- External codes are never used as foreign keys.

## 5. Foreign keys

- Always declare an FK constraint for relational columns.
- Choose `ON DELETE` deliberately:

| Behaviour | Use for |
|---|---|
| `RESTRICT` (default) | reference + historical data: `faculties`, `programs`, `sections`, `grades`, `invoices` |
| `CASCADE` | line items that are meaningless without the parent: `invoice_items`, `permission_role`, `section_lecturers` |
| `SET NULL` | optional links where the parent may vanish: `audit_logs.actor_id`, `*.recorded_by` |

- Index every FK column used in lookups, joins, `WHERE`, or `ORDER BY`.

## 6. Types

| Concept | Type |
|---|---|
| Ids | `bigint` |
| Short code/label/status | `varchar(n)` with `CHECK` |
| Text | `text` |
| Money | `numeric(12,2)` |
| Percentage / weight | `numeric(5,2)` |
| Score | `numeric(6,2)` |
| Grade point | `numeric(3,2)` |
| Credits | `numeric(4,2)` |
| Boolean | `boolean` |
| Date | `date` |
| Time-of-day | `time` |
| Instant | `timestamptz` |
| Semi-structured | `jsonb` — **only** audit snapshots, notification payload, settings value |

> `float`/`double` are **never** used for money, scores, credits, or GPA.

## 7. Statuses

- Strategy: **`varchar` + `CHECK` constraint** (never `enum`, never a lookup
  table). Rationale: see [`decisions.md`](./decisions.md) §5.
- Values are snake_case literals scoped to the column, e.g.
  `CHECK (status IN ('pending','partial','paid','overdue','cancelled'))`.
- Each status column is `NOT NULL` with a documented default.
- See [`data-dictionary.md`](./data-dictionary.md) for the full status tables.

## 8. Soft delete

- Add `deleted_at` **only** where history must survive a delete and the skill
  allows it (enrollments, grades, documents, invoices).
- Never soft-delete lookup/reference data (roles, rooms, grading scales,
  document types) — correct mistakes instead.
- High-value records use an audit trail instead of soft delete
  (`skills/audit-logging`): audit_logs, attendance, payments.
- Append-only tables (audit_logs, attendance_records, document_verifications)
  have **no** `updated_at`.

## 9. Uniqueness

- Only columns the business guarantees are UNIQUE.
- Composite uniqueness is ordered for readability, e.g.
  `(student_id, section_id)` for enrollment.
- Partial unique indexes express one-active rules, e.g. one active
  `student_programs` row per student.

## 10. Naming a constraint / index

| Object | Pattern |
|---|---|
| Unique | `uniq_<table>_<columns>` or Laravel semantic `unique([...])` |
| Index | `<table>_<columns>_index` (Laravel auto) |
| FK | `<table>_<column>_foreign` (Laravel auto) |
| Check | `ck_<table>_<column>` (name explicitly in raw SQL) |

## 11. Illustrative Laravel example

```php
Schema::create('enrollments', function (Blueprint $table) {
    $table->id();
    $table->foreignId('student_id')->constrained()->restrictOnDelete();
    $table->foreignId('section_id')->constrained()->restrictOnDelete();
    $table->foreignId('academic_year_id')->constrained()->restrictOnDelete();
    $table->foreignId('semester_id')->constrained()->restrictOnDelete();
    $table->string('status', 20)->default('pending');
    $table->timestamp('enrolled_at')->useCurrent();
    $table->timestamp('dropped_at')->nullable();
    $table->timestamps();
    $table->softDeletes();

    $table->unique(['student_id', 'section_id']);
    $table->index(['academic_year_id', 'semester_id']);
    $table->index(['section_id', 'status']);
});
```

> Column-level rules (lengths, `CHECK` status sets, defaults) are specified in
> [`schema-reference.md`](./schema-reference.md); the executable form lives in
> [`schema-tables.sql`](./schema-tables.sql).
```

## Validation checklist

1. snake_case plural tables; snake_case columns; `<entity>_id` FKs.
2. Single `bigint id` PK strategy; business IDs separate and UNIQUE.
3. Every relational column has an FK with a deliberate `ON DELETE`.
4. Statuses use `varchar` + `CHECK` only; defaults set.
5. Money/scores/GPA use `numeric`; never `float`.
6. `jsonb` only for audit snapshots, notification payload, settings value.
7. `deleted_at` only where the skill permits.
8. Append-only tables have no `updated_at`.
9. Related skills respected: `database`, `academic-domain`, `laravel`.

## Agent behavior (mandatory everywhere)

1. Inspect the existing implementation before modifying it.
2. Follow existing project conventions already established.
3. Do not rewrite working code unnecessarily.
4. Do not introduce technologies outside the EduCore stack.
5. Do not create unnecessary abstractions.
6. Do not create duplicate business logic.
7. Do not invent database relationships.
8. Do not bypass authorization.
9. Do not hardcode secrets.
10. Do not modify unrelated modules.
11. Run appropriate tests after changes.
12. Explain important architectural decisions.
